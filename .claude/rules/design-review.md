# 設計レビュー観点 <!-- omit in toc -->

Issue の設計レビュー・PR レビューで以下の観点を順に確認する。前提となる API・コードベースの知識は [eas-api-knowledge.md](./eas-api-knowledge.md) を参照。

## 1. 破壊的変更の判定（最重要）

v1.0.0（issue #43）で `--json` / `--csv` を削除した。以後、出力は人間向けテーブルのみで、列・文言・色・間隔はいずれもどのリリースでも変更されうる（互換性の保証なし・cosmetic）。テーブルのみの変更で破壊的変更（semver major）が発生することは基本的にない。

機械可読出力の要望が来て再追加する場合、以下の判定観点が再び効いてくる（フィールド名が変わらなくても破壊的変更になりうる点に注意）:

- フィールドの**意味**の変更（例: `periodStart/periodEnd` が「EAS請求期間」→「UTC暦月境界」、`buildsIos` が「EAS課金メトリクス」→「client-sideカウント」）は major。
- デフォルト出力の**行数・行の一意性**の変更（例: アカウント毎1行 → 月毎3行。アカウント名でユニークにキーしている消費者が壊れる）は major。
- フィールドの削除は major。フィールドの追加は minor。
- 「行数が増えるだけ」「フィールド名は同じ」という説明を鵜呑みにせず、**消費者側のパースコードを想像して**判定する。
- 判定結果は Issue に semver（changeset の major/minor/patch）として明記させる。

## 2. API の暗黙挙動に依存していないか

- **返却順序**: `builds(offset, limit)` 等の並び順は保証を確認できない。順序に意味がある機能はクライアント側ソートで保証する（`limit: 1` では顕在化しない前提が N 件で顕在化する典型例）。
- **上限値**: `limit` などの引数上限は明文化されていない。設計で決めた上限（例: 100）を API が実際に受け付けるか probe で事前確認する。
- **スキーマの罠**: ドキュメント上使えそうに見えて機能しないフィールドがある（`filterParams` 問題。knowledge 参照）。新しいクエリ形状は必ず probe で実挙動を確認してから設計を確定する。

## 3. 事前検証（probe-first）

- API の挙動に依存する設計判断には「事前検証」セクションを Issue に設け、`scripts/probe-*.mjs` での確認項目と、確認結果が想定と違った場合のフォールバック（例: バリデーション上限の引き下げ）を書く。
- client-side 集計を導入する場合は、EAS ダッシュボードの数字との突き合わせ検証をリリース前チェックに含める。

## 4. 時間・タイムゾーン

- 期間境界（暦月など）は **UTC 固定**を原則とし、Issue に明記する。実行環境のローカル TZ に依存させない（再現性・ダッシュボード突き合わせのため）。
- `billingPeriod.end` は**排他的境界**（次期間の開始瞬間）。人間向け表示は inclusive に補正するという既存方針を崩さない。
- 集計途中の期間（当月など）を確定値に見せない。人間向けテーブルは `(today)` 等で進行中と分かる表記にする。

## 5. 現在値と履歴値を混在させない

- 「現在」の値（プラン・ステータス・concurrency 等の契約情報）を、過去の期間の行に併記しない。「その時点の値」に見えて誤解を招く。
- 混在が必要に見えたら、表示モードの分割（例: `--usage` と `--plan`）を検討する。

## 6. 用語の統一

- 同じ概念は README・表ヘッダー・注記・HELP で**同一の表記**を使う（例: 成功ビルドは「successful build」で統一。「finished」「completed」と揺らさない）。
- 自前カウント値と EAS 公式メトリクスが混同されないよう、注記でデータ源を明示する。

## 7. API 呼び出し量の構造変化

- リクエスト数のオーダーが変わる変更（例: アカウント毎1回 → アプリ数×ページ数）は、呼び出し量モデル（何に比例するか）を Issue に明記させる（例: issue #18 の暦月化対応）。
- ガードレールを設計に含める: 並列数の上限（`mapWithConcurrency`）、遡り期間・件数の上限（バリデーション）、ページング走査の早期打ち切り。
- `gql()` にリトライ/バックオフは無い。呼び出し量が増える設計では 429 時の挙動（少なくともエラーメッセージ）を考慮する。

## 8. 権限・エラー劣化

- billing-scoped なクエリは権限のないトークンでアカウント単位に失敗する。**失敗しても run 全体を落とさず**、該当行を「-」にして理由を stderr に出す、が既定方針。
- データ源が複数クエリに分かれる設計では、「片方だけ失敗」時の表示を仕様として定義させる（劣化マトリクス）。データ源を減らして劣化パターン自体を消せないかも検討する。
- 標準出力（結果のみ）は汚さない（警告・進捗は stderr）。

## 9. Issue 運用・依存関係

- 実装前に Issue 化し、ユーザーの明示的な OK を待つ（CLAUDE.md のルール）。
- 複数 Issue が絡む場合、ブロック関係（Blocked by / Blocks）と推奨実装順を各 Issue 冒頭に明記する。同じファイルを触る Issue は小さい方を先行させる。
- 未確定の論点は「未確定事項」セクションに残し、決定したら仕様本文に昇格させる。

## 10. テスト・ドキュメント追従

- 仕様変更には対応するテスト（parseArgs のバリデーション、GraphQL 変数、出力形状、劣化挙動、回帰）を Issue の影響範囲に列挙させる。
- HELP テキスト・README・`.github/workflows/api-canary.yml`（クエリ形状変更時）・changeset の追従を影響範囲に含める。
