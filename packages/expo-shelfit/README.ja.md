> アカウント内のすべての Expo (EAS) アプリを、プラットフォームごとの最新ビルドバージョンとともに一覧表示 — **どのディレクトリからでも**実行できます。

> **非公式です。** Expo による提供・承認を受けたものではありません。作り上げたアプリを本棚に並べて眺める、という意味を込めた名前です。

```
$ npx @my-shelfio/expo-shelfit

┌─────────┬────────────┬────────────┬──────────┬─────────┬───────┬──────────┬─────────────────────┐
│ ACCOUNT │ APP        │ SLUG       │ PLATFORM │ VERSION │ BUILD │ STATUS   │ BUILD DATE          │
├─────────┼────────────┼────────────┼──────────┼─────────┼───────┼──────────┼─────────────────────┤
│ myorg   │ Storefront │ storefront │ ios      │ 3.2.2   │ 42    │ Errored  │ 2026/08/10-11:02:47 │
│ myorg   │ Storefront │ storefront │ android  │ 3.2.0   │ 38    │ Finished │ 2026/06/30-14:05:02 │
│ myorg   │ Field Ops  │ field-ops  │ ios      │ 1.4.0   │ 12    │ Finished │ 2026/05/28-18:40:11 │
│ myorg   │ Prototype  │ prototype  │ -        │ -       │ -     │ -        │ -                   │
└─────────┴────────────┴────────────┴──────────┴─────────┴───────┴──────────┴─────────────────────┘
```

## 🚀 機能

複数の Expo アプリを運用している場合、「今、どのアプリがどのバージョンか」にすぐ答える方法がありません — `eas build:list` はプロジェクトディレクトリの**内側でしか**動作せず、一度に1つのプロジェクトしか表示できません。`eas project:list` というコマンドも存在せず、Expo のダッシュボードでは各プロジェクトを1つずつクリックして確認する必要があります。`expo-shelfit` は EAS GraphQL API 経由でアカウント全体を走査し、1つの表にまとめて出力します。

- アカウント内のすべての Expo (EAS) アプリを、プラットフォームごとの最新のビルド**試行**とともに、**どのディレクトリからでも**一覧表示（成功したものだけでなく、エラー・キャンセルされたものも含む）
- `STATUS` 列に `Finished` / `Errored` / `Canceled` を表示。EASダッシュボードを開かなくても失敗ビルドに気づける
- `ios` または `android` に絞り込む `--platform` フィルター
- `--account <slug|name>` / `--app <slug|name>` — すべての表示モードに共通で、アカウントまたはアプリを1つに絞り込む
- `--local` — `BUILD DATE` をUTCではなくローカルタイムゾーンで表示
- `--history <N>` — 最新の1件だけでなく、プラットフォームごとに直近 `N` 件のビルド試行を表示
- `--stats` — UTC暦月ごとの成功/エラー/キャンセルのビルド数（デフォルトは直近3ヶ月、`--month <n>` で最大12ヶ月まで）。ビルド履歴からクライアントサイドで算出。`--group-by app` でアカウント単位ではなくアプリ単位に
- `--plan` — 現在のアカウントのサブスクリプション: プラン、プランID、ステータス、同時実行数、トライアル終了日
- `ACCOUNT` は EAS の「表示名」が設定されていればそれを表示し、なければ一意な slug にフォールバック
- ランタイム依存関係ゼロ

## 📦 インストール

```bash
npx @my-shelfio/expo-shelfit
```

インストールは不要です。もしくは:

```bash
npm install -g @my-shelfio/expo-shelfit
expo-shelfit
```

Node.js **22以降**が必要です（この CLI はグローバルの `fetch` を使用します）。

## 🔑 認証

**`EXPO_TOKEN`** 環境変数に設定したパーソナルアクセストークン — これが唯一サポートされる認証情報です。

```bash
export EXPO_TOKEN=xxxxxxxx
npx @my-shelfio/expo-shelfit
```

[expo.dev/settings/access-tokens](https://expo.dev/settings/access-tokens) で作成できます。

これは意図的に唯一の選択肢としています。トークンは `argv` から読み取られることも、ディスクに書き込まれることも、出力されることもないため、シェル履歴・プロセス一覧・置き忘れた設定ファイル・CLI自身の出力を経由して漏洩することがありません。送信先はただ1つ、EAS GraphQLエンドポイント（`https://api.expo.dev/graphql`）に、HTTPS経由で `Authorization` ヘッダーとして送信されます。`EXPO_TOKEN` が未設定の場合、CLI は非ゼロのステータスで終了します — プロンプトで待機することはなく、CI 上での実行も安全です。

> `EXPO_API_URL` でエンドポイントを上書きできます。これはローカルテスト用に存在するもので、この注記以外に文書化されておらず、互換性の保証対象外です。信頼できないホストを指定しないでください — そうするとトークンがそのホストに送信されてしまいます。

脆弱性を非公開で報告する方法は [SECURITY.md](../../.github/SECURITY.md)（英語のみ）を参照してください。

## 🛠️ 使い方

`-h` / `--help` でオプション一覧、`-v` / `--version` でインストール済みバージョンを表示します。

```bash
npx @my-shelfio/expo-shelfit --help
npx @my-shelfio/expo-shelfit --version
```

プラットフォームで絞り込む:

```bash
npx @my-shelfio/expo-shelfit --platform ios
```

アカウントまたはアプリを1つに絞り込む — 以下のすべての表示モードで共通して効きます:

```bash
npx @my-shelfio/expo-shelfit --account myorg
npx @my-shelfio/expo-shelfit --app storefront
npx @my-shelfio/expo-shelfit --account myorg --app storefront --history 5
```

`--account <slug|name>` はアカウントの一意な slug または EAS の表示名に一致します（大文字小文字を区別しない完全一致 — 部分一致はしません）。表示名が複数のアカウントに一致する場合は、代わりに slug を指定してください。`--app <slug|name>` も同様に slug または EAS の表示名に一致しますが、曖昧判定のスコープが異なります — 同一アカウント内で表示名が複数アプリに一致する場合のみ曖昧としてエラーになり（代わりに slug を指定）、別アカウントに同じ表示名のアプリがある場合は曖昧とせず両方一致します。`--app` はビルドを取得する*前*に適用されるため実行速度も向上します — アプリを取得しない `--plan` とは組み合わせられません。どちらのフラグも一致しない場合は終了コード1で「Did you mean」候補を表示します。

`BUILD DATE` はデフォルトで常にUTC表示です。ローカルタイムゾーンで見たい場合は `--local` を付けます:

```bash
npx @my-shelfio/expo-shelfit --local
```

```
┌─────────┬────────────┬────────────┬──────────┬─────────┬───────┬──────────┬─────────────────────┐
│ ACCOUNT │ APP        │ SLUG       │ PLATFORM │ VERSION │ BUILD │ STATUS   │ BUILD DATE (+09:00) │
├─────────┼────────────┼────────────┼──────────┼─────────┼───────┼──────────┼─────────────────────┤
│ myorg   │ Storefront │ storefront │ ios      │ 3.2.1   │ 41    │ Finished │ 2026/07/26-18:12:34 │
└─────────┴────────────┴────────────┴──────────┴─────────┴───────┴──────────┴─────────────────────┘
```

`--local` は `BUILD DATE` 列のみに効きます — `TZ` 環境変数にも他のNodeプロセスと同様に従います（例: `TZ=America/New_York npx @my-shelfio/expo-shelfit --local`）。列ヘッダにはタイムゾーン名の略称ではなく現在のUTCオフセットを表示します。オフセットなら対照表なしで読めるためです。それ以外の日付はすべてUTCのままです — `--stats` の `PERIOD`（暦月境界）や `--plan` の `TRIAL END` をローカル化すると、ビルドの集計月が黙ってズレてしまうためです。そのため `--local` は `--stats`・`--plan`（どちらも `BUILD DATE` 列を持たない）とは組み合わせられません。

プラットフォームごとの最新ビルドだけでなく、それ以上を表示する:

```bash
npx @my-shelfio/expo-shelfit --history 5
```

```
┌─────────┬────────────┬────────────┬──────────┬─────────┬───────┬──────────┬─────────────────────┐
│ ACCOUNT │ APP        │ SLUG       │ PLATFORM │ VERSION │ BUILD │ STATUS   │ BUILD DATE          │
├─────────┼────────────┼────────────┼──────────┼─────────┼───────┼──────────┼─────────────────────┤
│ myorg   │ Storefront │ storefront │ ios      │ 3.2.1   │ 41    │ Finished │ 2026/07/26-09:12:34 │
│ myorg   │ Storefront │ storefront │ ios      │ 3.2.0   │ 40    │ Finished │ 2026/06/30-14:05:02 │
│ myorg   │ Storefront │ storefront │ android  │ 3.2.0   │ 38    │ Finished │ 2026/06/30-14:03:47 │
└─────────┴────────────┴────────────┴──────────┴─────────┴───────┴──────────┴─────────────────────┘
```

`--history <N>`（1〜100、デフォルト: 1）は、各アプリ/プラットフォームを1行に集約する代わりに、プラットフォームごとに直近 `N` 件のビルド**試行**（ステータスを問わない）を別々の行として出力します。行は常にビルド日時の新しい順にソートされます — API のレスポンス順をそのまま信用するのではなく、クライアント側でソートしています。API の返却順はどこにも文書化されていないためです。`--platform` と併用できますが、`--stats` や `--plan` とは組み合わせられません。`--history 1` はフラグを付けない場合とまったく同じ出力になります。

アプリのバージョンではなく、暦月ごとの成功/エラー/キャンセルのビルド数を確認することもできます:

```bash
npx @my-shelfio/expo-shelfit --stats
```

```
┌─────────┬─────────────────────────┬──────────┬─────────┬─────────┬──────────┬───────┐
│ ACCOUNT │ PERIOD                  │ PLATFORM │ SUCCESS │ ERRORED │ CANCELED │ TOTAL │
├─────────┼─────────────────────────┼──────────┼─────────┼─────────┼──────────┼───────┤
│ myorg   │ 2026-08-01 → (today)    │ ios      │ 18      │ 3       │ 2        │ 23    │
│ myorg   │ 2026-08-01 → (today)    │ android  │ 16      │ 1       │ 0        │ 17    │
│ myorg   │ 2026-07-01 → 2026-07-31 │ ios      │ 14      │ 0       │ 1        │ 15    │
│ myorg   │ 2026-07-01 → 2026-07-31 │ android  │ 15      │ 2       │ 0        │ 17    │
│ myorg   │ 2026-06-01 → 2026-06-30 │ ios      │ 21      │ 1       │ 0        │ 22    │
│ myorg   │ 2026-06-01 → 2026-06-30 │ android  │ 20      │ 0       │ 1        │ 21    │
└─────────┴─────────────────────────┴──────────┴─────────┴─────────┴──────────┴───────┘
```

デフォルトは直近3ヶ月です。`--month <n>`（1〜12）でウィンドウを広げ、`--platform` で片方のプラットフォームの行だけに絞り込めます。

件数は API 経由のビルド履歴からクライアントサイドで算出しており、EAS 自身の課金/使用量メトリクスは参照していません — あれは請求サイクルに紐づき任意の暦月範囲に分割できないためです。したがって EAS ダッシュボードの数値と厳密には一致しない場合があります。実行中・キュー中のビルドは結果が未確定のため、3つのどのカテゴリにも `TOTAL` にもカウントされません。集計中の当月は、確定した件数ではないため終端を `(today)` と表示します。

`--group-by app` を渡すと、アカウント単位ではなくアプリ単位で集計します。`ACCOUNT` 列が `APP` 列に置き換わります:

```bash
npx @my-shelfio/expo-shelfit --stats --group-by app --month 1
```

```
┌────────────┬──────────────────────┬──────────┬─────────┬─────────┬──────────┬───────┐
│ APP        │ PERIOD               │ PLATFORM │ SUCCESS │ ERRORED │ CANCELED │ TOTAL │
├────────────┼──────────────────────┼──────────┼─────────┼─────────┼──────────┼───────┤
│ Storefront │ 2026-08-01 → (today) │ ios      │ 15      │ 3       │ 2        │ 20    │
│ Storefront │ 2026-08-01 → (today) │ android  │ 16      │ 1       │ 0        │ 17    │
│ Admin      │ 2026-08-01 → (today) │ ios      │ 3       │ 0       │ 0        │ 3     │
│ Admin      │ 2026-08-01 → (today) │ android  │ 0       │ 0       │ 0        │ 0     │
└────────────┴──────────────────────┴──────────┴─────────┴─────────┴──────────┴───────┘
```

「そのビルド数の増加はどのアプリが原因か」に、アプリごとに CLI を叩き直さずに答えられます。しかも**API 呼び出しは一切増えません** — アプリ単位の件数は元から取得されており、表示前にアカウント単位で合算していただけだからです。

その月にビルドが1件も無いアプリも、ゼロの行として必ず表示します。「このアプリはビルドされていない」ことが、行の不在ではなく値として見えるようにするためです。異なるアカウントに表示名が同じアプリがある場合も、行は分かれたままで合算されません（見分けるには `--account` を併用してください）。

失敗時の縮退もアプリ単位に細かくなります: ビルド件数の取得に失敗したアプリの行だけが `-` になり、アカウント全体は巻き込まれません。**アプリ一覧**の取得に失敗したアカウントは、アプリが分からないため行を1つも出さず、stderr に理由を出力します。

あるいは、ビルド件数や請求期間を含めず、アカウントの現在のサブスクリプションだけを確認することもできます:

```bash
npx @my-shelfio/expo-shelfit --plan
```

```
┌─────────┬────────────┬────────────┬────────┬─────────────────────────────┬───────────┐
│ ACCOUNT │ PLAN       │ PLAN ID    │ STATUS │ CONCURRENCY (TOTAL/IOS/AND) │ TRIAL END │
├─────────┼────────────┼────────────┼────────┼─────────────────────────────┼───────────┤
│ myorg   │ Production │ production │ active │ 2 / 1 / 1                   │ -         │
└─────────┴────────────┴────────────┴────────┴─────────────────────────────┴───────────┘
```

`--plan` はアカウントの**現在の**サブスクリプションのみを表示し、ビルド件数も請求期間も含みません — これらは「現時点の」事実であり、過去のデータと並べて表示すると各行に同じ値が繰り返されるだけになってしまうためです。`--platform ios` または `--platform android` を渡すと、`CONCURRENCY` をそのプラットフォームの数値だけに絞り込めます。`--stats` や `--history` とは組み合わせられません。3つとも独立した表示モードだからです。

### 数値の意味

| 列             | 出典                                                                                 |
| -------------- | ------------------------------------------------------------------------------------ |
| `ACCOUNT`      | アカウントの EAS「表示名」が設定されていればそれ、なければ一意な slug                |
| `APP` / `SLUG` | EAS のプロジェクト名と slug                                                          |
| `PLATFORM`     | `ios` / `android`                                                                    |
| `VERSION`      | 最新のビルド**試行**（ステータスを問わない）の `appVersion`                          |
| `BUILD`        | `appBuildVersion`（iOS のビルド番号 / Android の versionCode）                       |
| `STATUS`       | `Finished` / `Errored` / `Canceled` — それ以外のステータスは生の値を小文字化して表示 |
| `BUILD DATE`   | そのビルド試行が完了した日時（`YYYY/MM/DD-HH:mm:ss`、`--local` 指定時以外はUTC）     |

`--stats` の場合、代わりにアカウントごと・**UTC暦月ごと・プラットフォームごと**の1行になります（デフォルトは直近3ヶ月、`--month <n>` で1〜12ヶ月まで。`--platform` で一方に絞り込むまでは ios・android 両方の行が出ます）:

| 列         | 出典                                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ACCOUNT`  | 上記と同様 — アカウントの EAS「表示名」が設定されていればそれ、なければ一意な slug                                                                     |
| `PERIOD`   | UTC暦月。集計中の当月の終端は `(today)` と表示し、それ以外は月の最終日（inclusive）を表示（内部の境界値 `periodEnd` 自体は排他的境界）。               |
| `PLATFORM` | `ios` / `android` — アカウント×月ごとにプラットフォーム別の行になる                                                                                    |
| `SUCCESS`  | その月・そのプラットフォームで完了（Finished）したビルド数。API 経由のビルド履歴からクライアントサイドで算出 — EAS 自身の課金/使用量メトリクスではない |
| `ERRORED`  | 同様に、エラーになったビルド数                                                                                                                         |
| `CANCELED` | 同様に、キャンセルされたビルド数                                                                                                                       |
| `TOTAL`    | `SUCCESS`+`ERRORED`+`CANCELED` の合計                                                                                                                  |

実行中・キュー中のビルドはまだ結果が確定していないため、3つのどのカテゴリにも `TOTAL` にもカウントされません。`--platform ios` または `--platform android` を渡すと、そのプラットフォームの行だけを表示します（列構成は変わりません）。

`--plan` の場合、代わりにアカウントごとの1行になり、現在のサブスクリプションのみを表示します（ビルド件数・請求期間は含みません）:

| 列                            | 出典                                                                                                                  |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `ACCOUNT`                     | 上記と同様                                                                                                            |
| `PLAN`                        | `subscription.name`                                                                                                   |
| `PLAN ID`                     | `subscription.planId`                                                                                                 |
| `STATUS`                      | Expo が報告するサブスクリプションのステータス（`active`、`trialing` など）                                            |
| `CONCURRENCY (TOTAL/IOS/AND)` | 3つの同時実行数を一度に表示。`--platform` で1つに絞り込み可能                                                         |
| `TRIAL END`                   | `subscription.trialEnd`（`YYYY-MM-DD`）。アカウントがトライアル中でない（または一度もトライアルしていない）場合は `-` |

月額料金の列はまだありません — EAS のスキーマに存在するかどうかがまだ確認できていないためです。実トークンで確認できれば、後日追加される可能性があります。

**`VERSION` はローカルの `app.json` から読み取られたものではありません。** EAS はプロジェクト自体にバージョンを保存しないため、表示される番号は直近のビルド**試行**（ステータスを問わない）に焼き込まれたものです。一度もビルドされていないアプリは `-` と表示されます。

**`ACCOUNT` は EAS の「表示名」が設定されていればそれを表示し、なければ一意な slug にフォールバックします。** 表示名の方が読みやすい一方、一意性は保証されないためです。

### フィルタリング

- `--platform <ios|android>` — このプラットフォームのビルドのみ。このフィルターを設定すると、ビルドがゼロのアプリは特定のプラットフォームに一致しないため除外されます。`--stats` と併用するとそのプラットフォームの行だけに絞り込まれ（列構成は変わらず行数が半分に）、`--plan` と併用すると `CONCURRENCY` がアカウント合計ではなくそのプラットフォームの数値に絞り込まれます。
- `--account <slug|name>` — このアカウントのみ。一意な slug または EAS の表示名に一致（大文字小文字を区別しない完全一致）。すべての表示モードに効きます。一致しない場合は終了コード1で候補を表示します。
- `--app <slug|name>` — このアプリのみ。一意な slug または EAS の表示名に一致（大文字小文字を区別しない完全一致。曖昧判定は同一アカウント内のみが対象 — 上記参照）し、ビルド取得前に適用されます。`--plan`（アカウント専用でアプリを取得しない。併用は `CliError`）を除くすべての表示モードに効きます。一致しない場合は終了コード1で候補を表示します。
- `--local` — `BUILD DATE` をUTCではなくローカルタイムゾーンで表示します。効くのは `BUILD DATE` のみで、`--stats` の `PERIOD` や `--plan` の `TRIAL END` はUTCのままです。`--stats`・`--plan`（どちらも `BUILD DATE` 列を持たない）とは組み合わせられません。
- `--month <n>` — `--stats` との併用時のみ: ウィンドウを直近 `n` 暦月（1〜12、デフォルト3）まで広げます。
- `--group-by <account|app>` — `--stats` との併用時のみ: アカウント単位（デフォルト）かアプリ単位かを切り替えます。`app` を指定すると `ACCOUNT` 列が `APP` 列に置き換わります。API 呼び出しは増えません。
- `--history <N>` — 最新の1件だけでなく、プラットフォームごとに直近 `N` 件（1〜100）のビルド試行（ステータスを問わない）を新しい順に表示します。`--stats` や `--plan` とは組み合わせられません。

`--stats`、`--plan`、`--history` は互いに排他的な表示モードです — このうち2つ以上を組み合わせると `CliError` になります。

### 非推奨

- `--usage` — `--stats` の旧名です。現在も動作し、出力される表もまったく同じですが、stderr に非推奨の警告を出力し、次のメジャーバージョンで削除されます。改名の理由は、EAS の**請求上の**使用量と誤解され続けたためです（この CLI は請求スコープのフィールドを意図的に一切クエリしていません）。エラーメッセージには、実際に入力した方の名前が表示されます。

## 📚 ドキュメント

### 仕組み

`https://api.expo.dev/graphql` に対する3つの GraphQL クエリ:

1. `meActor { accounts }` — トークンが参照できるすべてのアカウント（テーブルの `ACCOUNT` 列にのみ使われる各アカウントの `displayName` を含む）
2. `account.byId(...).appsPaginated(first: 100)` — アカウントごとのアプリ、カーソルベースのページネーション
3. `app.byId(...).builds(offset: 0, limit: $limit, filter: { platform })` — プラットフォームごとの直近 `N` 件のビルド試行（ステータスを問わない、`--history` を指定しない限り `limit` は1）。レスポンスはクライアント側で `createdAt` の降順にソートされます。API の返却順自体は文書化されていないためです。

`filter` には意図的に `status` キーを含めていません — 実際の API で確認済みです（`scripts/probe-build-status.mjs`）。省略するとあらゆるステータスのビルドが返り、このフィールドは必須ではないことが確認できています。以前は `status: FINISHED` に固定していたため、エラー・キャンセルされたビルドは見えませんでした。現在は `STATUS` 列でそれを可視化しています。

ビルドクエリは同時実行数8で実行されます。ランタイム依存関係はゼロです。

`--stats` はステップ1〜2を再利用し、ステップ3の代わりに各アプリのビルドをページングして、クライアント側でプラットフォーム＋UTC暦月＋ステータスごとに集計します。`subscription`・`billingPeriod`・`usageMetrics` は一切クエリしません — これらは EAS の請求サイクルに紐づいており任意の暦月範囲に分割できず、また `metricsForServiceMetric` の `filterParams` は実際にはプラットフォームで絞り込めない（何を渡しても合算値を黙って返す）ことが判明しているためです。アカウントとアプリの取得は、入れ子にすると共有セマフォでデッドロックするため、2つのフラットなパスとして実行されます。

`--plan` はステップ2・3をスキップし、アカウントごとに `account.byId(...) { subscription }` のみを並列でクエリします。

## ❓ FAQ

**これは公式の Expo ツールですか？**

いいえ。EAS GraphQL API は**公式に文書化・バージョン管理されていません**。フィールド名は Expo 自身のオープンソースクライアント（[`eas-cli`](https://github.com/expo/eas-cli)、[`orbit`](https://github.com/expo/orbit)）から推測したものであり、予告なく変更される可能性があります。本プロジェクトは Expo による提供・承認を受けたものではありません。

**パーソナルアクセストークンの代わりにロボットトークンを使えますか？**

ロボットトークンは、それを発行したアカウントしか参照できません。所属するすべてのアカウントを一覧表示するには、パーソナルアクセストークンを使用してください。

**トークンがアカウントのアプリやビルドを読み取れない場合はどうなりますか？**

`--stats` はもはや請求スコープのフィールドを一切クエリしません — ビルド件数は各アプリのビルド履歴からクライアントサイドで算出されます。あるアカウントのアプリやビルドの取得が何らかの理由で失敗しても、そのアカウントの行は `-` 付きで出力され続け、理由は stderr に出力されます — 実行全体が失敗することはありません。

**なぜ一部のアカウントは `--plan` の列で `-` と表示されるのですか？**

プランデータは請求スコープです。トークンにアカウントの請求権限がない場合、その行はプラン列に `-` を表示したまま出力され、理由は stderr に出力されます。実行全体を失敗させることはありません。

**`VERSION` はローカルの `app.json` から取得されますか？**

いいえ。EAS はプロジェクト自体にバージョンを保存しないため、表示される番号は直近のビルド試行に焼き込まれたものです。一度もビルドされていないアプリは `-` と表示されます。

**`STATUS` が `Finished`/`Errored`/`Canceled` 以外の値を表示した場合は？**

この3つが、実際の API で現時点までに確認できている EAS ビルドステータスのすべてです（`scripts/probe-build-status.mjs`）。まだ実行中・キュー中のビルド — あるいはこの非公式APIが今後導入する他のステータス — は、親しみやすいラベルの代わりに生の enum 値を小文字化して表示します。行を壊したり隠したりするよりも、そのまま見える方を優先しています。

**`EXPO_TOKEN` がディスクに書き込まれたりログに出力されたりすることはありますか？**

ありません。`argv` から読み取られることも、ディスクに書き込まれることも、出力されることもありません。ポリシーの詳細と脆弱性を非公開で報告する方法については [SECURITY.md](../../.github/SECURITY.md)（英語のみ）を参照してください。
